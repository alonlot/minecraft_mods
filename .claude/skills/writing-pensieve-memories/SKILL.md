# Writing Pensieve Memories

A memory is one JSON file: a built set, actors, timed events, words and a camera. Everything the viewer sees is
a pure function of the scene clock, so you author it as data and never write Java. The parser rejects unknown
keys with the JSON path, so a typo is loud. Source of truth if this file ever disagrees with the code:
`pensieve/scene/SceneParser.java`, `SceneValidator.java`, `SceneNames.java`, `CameraTrack.java`.


**Recorded memories are not hand-authored.** A player captures one with an Empty Memory Phial (sneak, wand in the other hand). It is saved as a `Recording` in a `.hpm` file under `<world>/data/hogwartsmagic_memories/` and plays as the scene `recorded/<uuid>` (`RecordingScene`), whose start packet carries empty JSON; the client builds the set, actors, beams and sounds from the `Recording` itself. Do not write JSON for them; this skill covers authored story memories only.

## Step 0 - Shot list first

Before any JSON, write (in your reply) the beats and shots: what happens, who is where, one line per shot with
its start time, length, framing and camera move. Check the total against `length`. Then write the JSON.

## Film craft rules

- Establish the place with a wide, slow shot first (fov 70 or more, camera drifting).
- Cut on action: put a `"cut": true` key on the swing, the cast, the fall, not between beats.
- Keep shots 2-6 seconds. Under 2 reads as a glitch, over 6 drags.
- Move the camera while actors move (a slow dolly or arc), lock it off for still moments.
- Hold on the key moment: ease in, then 1-2 seconds of nothing new.
- Narrow the fov (40-55) for close-ups, widen (80-100) for scale or dread. Roll 3-8 degrees for unease.
- Give every spell a wind-up (pose `wand_raised`), the cast, then a reaction (`hurt`, `die`, `cower`) 5-10 ticks later.
- End on a slow push-in (pos moves 1-2 blocks over 3+ seconds, fov narrows) before the fade; the fade is automatic at `length`.
- Dialogue (`words`) lasts 8 s on screen; space lines 2+ s apart. Narration is centred, italic, default 4 s.

## Scene format

Times are ticks (20 per second) as a number, or seconds as a string: `40` or `"2s"` or `"2.5s"`. Any time must lie
in `0..length`. Positions are blocks relative to the set origin (see Coordinates). Unknown keys are errors.

### Top level
| key | type | default | notes |
|---|---|---|---|
| `title` | string | the file id | |
| `length` | time | required, > 0 | scene ends and fades here |
| `radius` | int | 40 | max 200; everything in `set` must fit within +-radius of origin in X and Z |
| `fog_far` | int blocks | none | opt-in far view: without it the void fog closes in just past `radius` (start radius-8, end radius+2), so nothing beyond ~radius shows. With it the fog is a soft haze from 75% of `fog_far` to `fog_far` (`PensieveTimeline.farFog`), growing and collapsing with the reveal like the default, and never past the viewer's own render-distance fog (12 chunks = 192 blocks). 1 to 512. For a distant backdrop; `lake_patronus` uses 200 for Hogwarts across the lake. The edge fragments still sit at `radius` |
| `set` | object | empty set | below |
| `poses` | object | none | custom poses, below |
| `actors` | array | none | below |
| `events` | array | none | below |
| `words` | array | none | below |
| `camera` | array | none | empty = viewer looks freely; otherwise directed |
| `next` | string | none | id of another memory scene (lowercase `[a-z0-9_]+`, not this scene's own id) to chain into when this one ends; whether it exists is checked when the hand-over happens, not at validation. A chained scene fades to black over its last 20 ticks (instead of the exit), the viewer is moved to the next scene (built ahead in its own slot while this one plays), the screen stays black until the new set has arrived and is drawn around the first shot (at most 60 ticks, `PensieveTimeline.HANDOVER_HOLD_LIMIT`; the next scene's clock is already running, so keep its first second or so free of anything that must be seen), and it fades in from black over 20 ticks, darkness only (no fog-from-two-blocks reveal as on entering), with its own actors, sounds and time of day; nothing of the last scene carries over except music still fading out over 20 ticks |
| `handover_colour` | string | `black` | `black` or `white`; valid only with `next` (`white` without `next` is an error). `white`: this scene's 20-tick chain fade goes to white instead of black, the hold while the next set arrives stays white, and the next scene's 20-tick fade-in comes from white (the client keeps the colour across the hand-over). The `eyes_*` lids stay black, and a mid-scene `handOver` and an early leave are always black. Use it for a flash of light (a blinding spell, a crash into sunlight) and let the next scene open on something bright, or the fade-in reads as a cut. Pure maths: `PensieveTimeline.handoverColour`; drawn by `PensieveOverlay` (white) and `PensievePost` (black) |
| `end_action` | string | none | `wake` or `cave_map`. **`wake`**: a viewer going home from this scene by its end or by leaving early (not a yank or a broken basin) wakes up in the real world: the server sends the wake just before the move home, the client holds the screen black through the return (no silver draining away), then once the dive is over the lids open on the real world with the `eyes_open` curve over 40 ticks (`PensieveSessions.WAKE_TICKS`; the one lid effect drawn outside a memory, with the HUD still hidden until it ends). It needs no `sawStart` (it is only a picture). Server code that should follow the wake waits `PensieveSessions.WAKE_DONE_TICKS` (60) after the home callback (the Sorting's house reveal does). Used by `locket_cave` (whose 80 Inferi and Fiendfyre, `locket_cave.py`, are the worked example of a crowd: ring slots round the hero, straight radial paths, everything timed off the fire's wavefront, `write_scene(..., width=400)` to stay under the size cap) |

### `set`
| key | type | default | notes |
|---|---|---|---|
| `templates` | `[{id, at:[x,y,z]}]` | none | `.nbt` structure templates (`data/hogwartsmagic/structure/*.nbt`, id `hogwartsmagic:<name>`); the template's corner is placed at `at`. Sizes (x,y,z): see below. Shipped: black_lake_ruin, chamber_hall, death_eater_camp, diagon_alley, fen_gibbet, goblin_vault, hogwarts_ruin_camp, horntail_nest, locket_cave, merfolk_village, willow_clearing |
| `schematics` | `[{id, at:[x,y,z], rotation?}]` | none | a bundled Sponge schematic; only `mini_hogwarts` (96 x 109 x 145, about 36,400 non-air blocks, its own rocky hill included; `worldgen/MiniHogwartsSchematic`). `rotation` 0/90/180/270 clockwise from above (default 0) turns positions and block states; the rotated footprint (145 x 109 x 96 at 90/270) has its min corner at `at`. Air and command blocks are skipped; cells beyond the radius are cropped; cleared with the set. Only the anchor is validated, so fit anchor + footprint inside +-radius yourself. Generators: `schematic_grid`/`rotate_xz` in `scene_common.py` give the same cells and rotation as `SetBuilder` |
| `fills` | `[{block, from:[x,y,z], to:[x,y,z]}]` | none | solid box; max 2,000,000 blocks each; inside the radius |
| `disks` | `[{block, center:[x,y,z], radius}]` | none | flat horizontal disc at `center` y; inside the radius |
| `features` | `[{id, at:[x,y,z]}]` | none | configured worldgen features (e.g. trees), id like `minecraft:oak`; only the anchor is checked |
| `time_of_day` | number | 18000 | day time at the set: 0 dawn, 6000 noon, 12000 dusk, 18000 midnight |
| `build_ticks` | int ticks | 60 | how long the dive waits while the set builds |

Later entries overwrite earlier ones where they overlap (templates first, then schematics, then fills, then disks), but a template or schematic does not carve holes in a fill beneath it: their air is skipped. A fill can therefore re-block cells of a schematic (`lake_patronus` lights Hogwarts' windows with single-cell glowstone fills over its black glass, picked in the generator).
Block ids are namespaced (`minecraft:stone_bricks`).

**Extent trap:** the validator checks only a template's or feature's *anchor* against the radius. `SetBuilder` then silently crops every block more than `radius` from the origin (X or Z), with no error. So make sure anchor + template size fits inside +-radius, and raise `radius` (max 200) for big templates. Template sizes (x,y,z) from each `.nbt`'s `size` tag: black_lake_ruin 15x9x15, chamber_hall 51x32x101, death_eater_camp 27x14x27, diagon_alley 233x45x49 (wider than radius 200 even when centred: crops), fen_gibbet 10x13x10, goblin_vault 17x8x11, hogwarts_ruin_camp 39x17x29, horntail_nest 14x5x14, locket_cave 64x42x64, merfolk_village 25x14x25, willow_clearing 23x3x23. For a new template, read it: `python -c "import gzip,struct;d=gzip.open('f.nbt').read();i=d.find(b'\x09\x00\x04size')+7;print(struct.unpack('>3i',d[i+5:i+17]))"`. Centre a template with `at` = minus half its x/z size.

**Physics trap (unsupported gravity blocks and open water edges):** the set is placed with no neighbour updates and the server clears the block and fluid ticks each placement schedules, so nothing falls or flows while the memory plays. Do not lean on that. Gravel, sand or concrete powder over nothing (template air counts as nothing: air in a template is skipped, and below the set is void) collapses into falling blocks the moment anything updates it, and water beside or above an empty cell, or at the radius edge, drains into the void. Put a solid layer (stone, deepslate) under every seabed and lake bed, and close every water edge with rock or a `minecraft:barrier` rim. In a generator, build a `world` dict of the set (cell to block id) and add `problems += physics_problems(world, R)` from `scene_common.py`: it lists unsupported gravity blocks and open water edges, and `unsupported_gravity(world)` gives the cells that need a block under them (`locket_cave.py` fills them with deepslate).

### `actors[]`
Keys: `id` (required, unique), `type` (required), `skin`, `name`, `items`, `path`, `look`, `limbs`, `poses`, `anims`, `actions`, `scale`, `life`, `block` (`memory_block` only), `ride` (a rider of a vehicle: a `memory_rowboat`, `memory_broom` or `memory_broom_racing`; see **Riding** below).

- `type`: `"player"` (a skinned humanoid) or a namespaced entity id (`hogwartsmagic:troll`, `minecraft:zombie`). Mobs have no AI, no gravity, no collision.
- `hogwartsmagic:memory_letter`: a flat Hogwarts-letter envelope you path like any actor. `look` pitch 90 lays it flat and pitch 0 stands it upright (the renderer and the letter flood agree); its two faces both show the envelope. It flutters (roll and wobble) in proportion to its speed: still at 0, full strength from 0.05 blocks per tick (1 block a second), linear between, so a path that slows or holds settles it smoothly (`LetterFlutter.amplitude`). The flutter phase comes from the actor id, so it is the same every replay.
- `hogwartsmagic:memory_door` and `hogwartsmagic:memory_door_mirrored`: one hinged door leaf, 1 wide x 3 tall x 0.2 thick at `scale` 1 (`scale` multiplies all three). The actor `path` position is the hinge's bottom corner on the leaf's near face (local z = 0), and `look` yaw swings the leaf about that edge. `look` pitch also tips the leaf about its bottom edge on the front face (the thickness side, local +Z), in the leaf frame before the yaw: 0 is upright (and a scene that keys only yaw renders exactly as it always did), -90 has the top fall toward the front until the leaf lies flat on its front face, a slab of its own thickness on the floor, the top edge a leaf-height (3 x `scale`) from the bottom edge. The bottom edge on the front face stays where the upright leaf had it, so a fallen leaf is no longer pinned to the hinge: yaw sets which way it falls (the front faces the way the leaf's thickness points, so for the plain leaf yaw -90 falls toward -X) and the hinge breaking is a yaw key then a pitch key. Pitch ranges over [-90, 90] and is smoothly interpolated like yaw (verified by `DoorHingeTest.fallsAboutBottomEdge` and `pitchAndYawCompose`). A real door pair is one of each, at the same yaw, so both leaves' thickness is on the same side and they sit flush. Faces carry an iron ring on a stud near the meeting stile; the ring is real 3D geometry that swings as a damped pendulum with the leaf's angular acceleration (it lags a start, kicks on a stop) and a sudden stop (over 8 degrees per tick of yaw speed lost) gives a 4-tick 0.3 degree shudder; all automatic. Lit from the brightest light around the leaf, not at the hinge.
  - Plain leaf (`memory_door`, extends from the hinge toward local +X): yaw 0 puts the free edge on +X, -90 on +Z, 90 on -Z, 180 on -X. Thickness is on local +Z (world: yaw 0 +Z, -90 -X, 90 +X, 180 -Z).
  - Mirrored leaf (`memory_door_mirrored`, local x negated, extends toward local -X): yaw 0 puts the free edge on -X, -90 on -Z, 90 on +Z, 180 on +X. Thickness is still on local +Z.
  - Yaw direction: turning the plain leaf toward more negative yaw swings its free edge from +Z round to -X (yaw -90 to -180); the mirrored leaf swings the other way (yaw -90 to 0, increasing). Keep yaw continuous (do not wrap -180 to 180).
  - Hinge placement: put the hinge exactly on the jamb. The leaf thickness does not extend toward the jamb when closed (it lies along X), so no offset is needed; when open, the thickness (0.2 x `scale`) lies on the jamb side of the hinge, sinking into a side wall at the jamb plane, which is hidden. Only if the open leaf must sit flush against a wall face at the jamb, move each hinge 0.2 x `scale` toward the doorway centre and accept a gap of that size at the jamb when shut.
  - Worked example (verified by `DoorHingeTest.pairMeetsAndOpensTheSameWay`): a doorway 8 wide along Z (jambs at z = -3.5 and z = 4.5), the wall plane at x = X0, leaves at `scale` 4 (4 wide, 12 tall, 0.8 thick) opening toward -X. Low leaf: `memory_door`, path `[X0, y, -3.5]`, yaw closed -90 (spans +Z to z = 0.5), open -180 (lies along -X). High leaf: `memory_door_mirrored`, path `[X0, y, 4.5]`, yaw closed -90 (spans -Z to z = 0.5), open 0 (lies along -X). Both are closed at yaw -90, meeting at z = 0.5 with their thickness on the -X side; the low leaf opens by turning -90 to -180 and the high leaf by turning -90 to 0, so they swing as mirror images. To open toward +X instead, swing the low leaf -90 to 0 and the high leaf -90 to -180 (the closed pose is the same).
- `hogwartsmagic:memory_banner_gryffindor`, `_hufflepuff`, `_ravenclaw`, `_slytherin`, `_hogwarts`: a tall hanging cloth banner (the film's Great Hall banners: the house's beast on its colours, or the Hogwarts crest), 2 wide x 8 tall at `scale` 1 (`scale` multiplies both), the point and gold fringe included. The actor `path` position is the middle of the gold hanging rod at the top; the cloth hangs straight down from it, so put it just under the ceiling (in the Great Hall, 0.08 under the enchanted ceiling's plane). The front, where the art reads normally, faces the actor's `look` yaw (Minecraft convention: -90 faces +X); the back shows the same art the right way round. The cloth sways very gently on its own (pure function of the scene clock and the actor id, `pensieve/scene/BannerCloth`): the top edge stays put, the foot swings up to 0.31 blocks out of the plane and drifts 0.07 sideways (times `scale`), each banner on its own periods. Give it one path key and one yaw and leave it; a moving path is not meant for it. Lit from the brightest light round each band of the cloth (both edges, a block in front and behind), blended down its length; the floating candles light nothing, so put a `minecraft:light` block a couple of blocks in front of each banner (a `block` event at `t` 0). Keep floating candle boxes and the camera out of the sway volume (`great_hall_scene.py` `check_banners` does both).
- `hogwartsmagic:memory_block`: one block state drawn through the block renderer (its baked model, as the block looks placed in the world): bricks of a wall that opens, wand boxes off a shelf, a vase. `block` (required, and only on this type) is the state: `"minecraft:bricks"` or with properties `"minecraft:oak_stairs[facing=east,half=top]"`. The validator checks the shape and the block id; a property the block does not have is caught by the game's parser on the client (logged, the actor shows nothing), so preview once. The `path` position is the block's **centre** (a block resting in grid cell `[x, y, z]` is at `[x+0.5, y+0.5, z+0.5]`), and `look` turns it about that centre: `yaw` (Minecraft convention: 90 turns its south face to the west), `pitch` (positive tips its south face down), and `roll` (degrees about its own north-south axis, applied last; `roll` is only for this type). All 0: exactly as placed. `scale` scales it about the centre. Lit at its centre. Yaw, pitch and roll are interpolated per tick without wrapping, so a tumble is just a big number (`"pitch": 360`), but keep each tick's yaw change under 180 degrees. Cheap in the hundreds: each state's quads are gathered once and every block of a frame goes into one batch (about 24 vertices and one light lookup per cube; 400 tumbling bricks are fine). Dev scene: `run/pensieve_dev/dev_blocks.json` (400 bricks rippling out of a wall in tumbling arcs).
- `hogwartsmagic:memory_tape`: a cream cloth measuring tape, ticked and numbered, with brass caps at both ends. The actor is its free end; the rest (1.5 blocks long at `scale` 1, 0.07 wide) trails behind along the actor's own `path` over the last 3 s, and whatever the path does not cover (it has just started, it holds still, or it moves slower than its length per 3 s) hangs straight down. A pure function of the scene clock (`pensieve/scene/TapeTrail`), so a late joiner sees the same tape. The flat of the tape stands upright (a tape circling the boy wraps him like a belt) with a slow ripple. Path it with `linear` keys every 2 to 4 ticks: for measuring, a rising spiral round the boy (radius about 0.7, one turn per 2 s, climbing 0.2 blocks a second). No `look` needed. Dev scene: `run/pensieve_dev/dev_wand_choice.json`.
- `hogwartsmagic:memory_rowboat`: a small wooden rowing boat, 4 blocks long and 2 wide at `scale` 1 (`scale` multiplies it): tarred planks outside, weathered planks, ribs and bottom boards inside, a rubbing strake, keel, flat transom and stem post, three thwarts, iron oarlocks and two oars (built in Java from the curves in `pensieve/scene/Rowboat`, no texture of its own). Boat-local frame: x is the boat's left (port) side at yaw 0, y up, z forward to the bow; the origin is the waterline at the middle of the hull, so its `path` is the **still-water** position (put `path` y at the sea's `at` y). Give it a `look` yaw (Minecraft convention) along its course; without one it faces the way its path heads (and keeps its last heading while it holds still). **Riding the sea:** at each moment the boat takes the `rough_sea` event running then whose area contains its path position, the nearest centre if several do (`RoughSea.bind`); with none it sits level on its path. It samples the waves under a 3 x 5 grid over its footprint and fits a plane: the mean is the heave, the slopes its pitch (bow up positive) and roll (left side up positive), so it rises, pitches and rolls with every swell (verified: the waterline stays within 0.15 blocks of the surface at every intensity from 0.1 to 1, `RowboatTest.boatRidesTheSurface`). **A boat may only ride a sea of intensity 1 or less:** above that the shorter swells outgrow what a 4-block hull can follow, so the validator rejects a scene where a `memory_rowboat`'s path (checked every 5 ticks and at each key, with the same binding) lies over a running `rough_sea` stronger than 1 (`RoughSea.MAX_BOAT_INTENSITY`). Seas with no boat on them may go to 2. The waves never show inside the hull (the sea draws a depth-only lid over it first), although the bottom boards are below the waterline. **Oars:** they stroke on their own while the boat moves, at full stroke from 0.04 blocks per tick (0.8 a second) of path speed, measured over the 10 ticks round now, easing to rest (trailed aft) as it stops. One stroke is 52 ticks (`Rowboat.OAR_PERIOD`), its phase `s = (t / 52) mod 1` from scene time 0: the catch at s 0 (sweep 40 degrees, blade toward the bow), the drive to the finish at s 0.5 (sweep -22, the sweep being `9 + 31 cos 2 pi s`), then the recovery with the blades lifted and feathered flat; blades splash at the catch and finish and the bow throws spray when it slams into a wave. Key the rower's arms to that phase (`dev_storm.py`'s `rower_limbs`: arms -80 at the catch to -38 at the finish, `"mode": "set"`, body leaning 14 forward to 10 back). The oarlocks sit 0.2 aft of the middle, on the gunwale; `Rowboat.handle(oar)` gives the left handle in boat space if a generator wants exact hands.
  - **Riders:** an actor with `"ride": "<boat id>"` (any type but a vehicle; the validator checks the id is a vehicle and not itself; a window works as for every vehicle, see **Riding**) sits in that boat: its `path` is an **offset in the boat frame** (blocks, multiplied by the boat's `scale`; key it to move a rider about, it is at the offset for the whole scene) and its `look` yaw is **relative to the boat** (0 faces the bow); it heaves, pitches and rolls with the boat (its whole model tilts about its root). A rider is never walked by the boat's motion. Seats at boat scale 1, as the rider path offset `[x, seat_top - 0.5722 x rider scale, z]` with seat top 0.12 (`Rowboat.SeatSpot.offset`): `oars` (the rower, middle thwart) `[0, -0.4522, 0.15]` at 1.0, look yaw 180 (facing the stern, as a rower does); `stern_left` `[0.42, -0.4522, -1.38]` at 1.0 and `stern_right` `[-0.38, -0.3092, -1.38]` at 0.75 (side by side on the stern thwart, yaw 0, facing the rower); `bow` `[0, -0.3092, 1.3]` at 0.75, yaw 180 to face the others or 0 to look ahead. Pose riders seated with the legs at -65 (`{"right_leg": [-65, 8, 0], "left_leg": [-65, -8, 0]}`): their feet then rest above the bottom boards (y -0.20) and clear the next thwart; the seated life layer (slouch, sway, hands in the lap) still runs. To step out at a landing, end the scene there, or move the rider's offset over the side while the boat holds still.
  - Dev scene: `run/pensieve_dev/dev_storm.json`, written by `build_scripts/pensieve_scenes/dev_storm.py` (a 92-block sea under rain at night with lightning, a rock for shore foam, the boat rowed across with the four riders, the rower's arms keyed to the stroke); `SceneDataTest.devStormSceneValidates` validates it when it exists.
- `hogwartsmagic:memory_broom` (the school broom: the real broom's model, BroomModelV2's training layer and texture) and `hogwartsmagic:memory_broom_racing` (the Nimbus layer and texture): at `scale` 1 the size of the real broom. **Broom frame** (`pensieve/scene/BroomFlight`): x is the broom's left, y up, z toward the handle's tip; the origin is the **seat point on the handle axis**, so its `path` is where a rider's hips sit (the seat top is 0.06 above the axis). The model reaches 1.68 ahead and 1.97 behind (school; Nimbus 1.22 / 1.74), and hangs down to -0.38 at the brush (Nimbus -0.51); `scene_engine.broom_box` / `broom_lowest` give the box and its lowest world point. **Orientation:** `look` takes `yaw`, `pitch` (nose down positive, as for heads) and `roll` (the bank, right side down positive; `roll` is allowed on the broom types). Without `look` the yaw follows the heading (keeping the last one while it holds still or rises straight up), the pitch the climb angle (clamped to +-70, smoothstepped to level below 0.05 blocks a tick, so a hover is level) and the roll is the **auto-bank**: 1000 x the sideways acceleration (blocks/tick^2, from the path at t and 3 ticks either side), softly limited to 45 by a tanh, faded out with speed below 0.05; a right turn (yaw increasing) banks right side down, a 0.5 blocks/tick turn of radius 12 banks about 20. With `look` but no `roll` key the roll is still the auto-bank. **Bob:** while it carries a rider a slow broom bobs 0.04 at 0.9 Hz (phase from the broom id), fading out by 0.1 blocks a tick and eased in and out with the rider's window; an empty broom holds dead still. A broom `look_at` aims at its origin (the seat point). **Baked headings:** a generator that keys a broom's `look` from its path should sample `scene_engine.broom_heading_held` (Java `BroomFlight.heldHeading`, opt-in: below 0.01 blocks a tick of firm horizontal speed it keeps the last forward heading, a spline overshoot creeping back under 0.15 counts as still, from 0.06 it is exactly the heading; parity `heading_cases.json`, `BroomHeadingTest`) and not `broom_heading`, whose widening window faces a hovering broom backwards and then snaps it round; blend the heading in by horizontal speed and turn each key at most 9 degrees a tick (`flying_scene.steady_yaws`; a spline run's middle turns up to 1.5x its keys' rate), and assert the drawn yaw rate (`flying_scene.check_yaw_rates`: at most 15 degrees a tick, quarter-tick samples of `broom_pose`): 110 to 180 degrees in 4 ticks reads as the broom and its rider spinning. Path a flying broom with `spline` keys (see Ease): `linear` keys make the bank and the climb pitch step at every key. Keep a flight under about 0.12 blocks/tick^2 of speed change.

The server fills it in the scene JSON before sending it (so every viewer sees the same wand) from the start context: the wand the player just bought when mod code starts the memory with `PensieveSessions.startSolo(player, sceneId, Map.of(ItemText.CONTEXT_WAND, wandId))`; otherwise (a dive, a preview, a plain `startSolo`) the wand in the starter's main hand, then off hand (an item whose id ends in `_wand`), then `hogwartsmagic:harry_potter_wand`. Every scene of a chain (`next`, `handOver`) gets the same wand. `{reject_wand_1}`, `{reject_wand_2}` and `{reject_wand_3}` work the same way and become three distinct wands that are never the viewer's (`ItemText.rejects`: the wandmaker's sold wands first, then the rest, in a fixed order, so a given viewer wand always gets the same three): use them for the wands that are tried and turned away. A word or name reading "{viewer_wand}" or "{reject_wand_N}" is left as written. A purchase (or held item) that is not a wand never becomes the viewer wand.
- `path`: `[{t, pos:[x,y,z], ease?}]` - the feet position (a broom's: its seat point; a rider's inside its ride window: the offset in the vehicle frame). Holds the first value before the first key and the last after it. The body turns to face its movement unless `look` is given.
- `look`: `[{t, yaw, pitch?, roll?, ease?}]` - body and head yaw, head pitch (default 0). Overrides movement facing. `roll` (default 0) is only for `memory_block`, `memory_broom`, `memory_broom_racing` and `memory_horntail`; on any other type a non-zero roll is a validation error.
- `limbs`: `{ "<part>": { "rot": [{t, v:[x,y,z], ease?}], "offset": [{t, v:[x,y,z], ease?}], "mode": "add"|"set" } }`. `rot` is degrees, `offset` is model pixels (16 px = 1 block). `mode` default `add` (added on top of the current animation); `set` replaces it. Applied last, over poses and creature animations.
- `poses`: `[{t, name, blend?}]` - a preset or a custom pose from top-level `poses`; stays until the next cue. `blend` is the ticks to ease in; 0 or absent means the default 5, so use `"blend": 1` for an instant pose.
- `anims`: `[{t, name, blend?}]` - a creature animation by name (table below), or for a `player` a player clip (Player motion below). Case-insensitive; stays in force until the next cue. Creature animations: `blend` fades the new clip in from the rest pose over that many ticks (0 = instantly); the previous clip stops at once, it is not cross-faded. Player clips cross-fade from the previous clip over `blend` ticks (0 or absent = 4; 1 for a near cut). The validator rejects an unknown player clip name; creature names are checked in a preview (chat error).
- `actions`: `[{t, do, spell?, target?, item?, slot?, duration?}]` (`duration` only on `breathe`).

Ease: `linear`, `in`, `out`, `in_out` (cubic). Default `in_out`. The ease belongs to the segment that ends at that key. Camera keys and actor `path` and `look` keys also take `spline`: the same C1 Hermite as the camera's (see `camera[]`: inner velocity `(h1*d0 + h0*d1)/(h0+h1)`, the eased neighbour's speed at a run end, natural first and last ends; `Track.sample`), so a flier or a walker keyed densely keeps a continuous velocity; end a run with an `in_out` key to come to rest. Everything that reads a path (the gait, the owls' `Airborne`, the brooms' bank, climb and bob, `RoughSea.bind`, the letter flutter) reads the splined position; the Python mirror is `scene_engine.track_sample` (`sample_path` uses it). `limbs` keys reject `spline`.
Keyframes between keys are interpolated per component; yaw is NOT unwrapped, so keep yaw continuous (say 90 then 180, not 90 then -180).

### Player motion (life and clips)
Every `player` actor moves like a person without any keys: `pensieve/scene/HumanMotion` (pure maths, unit tested), applied on the client by `client/pensieve/ActorMotion`. All of it is a function of the scene clock and a seed from the actor `id`, so a late joiner sees the same thing and no two actors move in lockstep: each has its own tempo, phase, energy, handedness and timing jitter.

**Life** (always on unless `"life": false`), small and additive:
- breathing: shoulders and chest rise and fall every 3.4-4.6 s (asymmetric: quicker in, a pause after out);
- the gaze drifts a few degrees on top of `look`;
- standing: the weight sits on one leg and shifts every 4.5-8 s (the hips slide over the standing leg, the other knee eases, the shoulders lean back over the middle);
- walking, from the real path speed: stride and arm swing matched to speed (a stride, two steps, of about 1.15 / 1.4 / 1.75 / 2.4 blocks at 0.6 / 1.4 / 2.5 / 4.5 blocks per second at scale 1, legs swinging about +-22 / 28 / 36 / 53 degrees; scale both distance and speed with the actor), arms against the legs a beat late, shoulders counter-twisting with the head turning back to keep the gaze, hips sinking as the legs spread and sliding over the standing leg, a forward lean that grows with speed, a step nod. The stride phase is locked to the distance walked along the `path` (the feet do not slide; it holds when the path holds), averaged over 6 ticks so the gait eases in and out with the path's own ease. The vanilla walk animation is off for a living actor;
- a head lead: with `look` the head goes where `look` says at once and the body follows a few ticks behind (a smooth lag, mean about 5 ticks, no overshoot; still clamped to 75 degrees from the head);
- seated (a pose cue whose `right_leg` or `left_leg` x is -60 or less, or a seated clip): a slouch of 4-9 degrees at the hips, the head lifted back to the eye line, hands in the lap (arms -30 to -42), a slow sway; no gait;
- off while the actor is `stone` or dying. Parts the actor keys in `limbs` get 35% of the life (0 in `"mode":"set"`), so hand-keyed idle motion is not doubled.

**Clips** (player `anims` names; L = loops until the next cue, 1 = one-shot). A clip owns the parts it drives (their rotation is replaced, blended by the cue weight) and adds secondary motion (bounces, nods, leans at the hips) on top of the rest. `IDLE` ends a clip (cross-fades back to life and the pose).
| clip | | what it does |
|---|---|---|
| `IDLE` | L | no clip: life and the pose only |
| `CLAP` | L | hands meet in front of the chest 2.2-2.8 times a second, rhythm drifting per actor; one hand travels more; a dip on each contact, a small body and head bounce |
| `CHEER` | L | a dip, arms thrown up past the top (0.3 s) into a V, then fists pumping 1.6-2.3 times a second (together, a beat apart, or alternating), bouncing on the seat, head back shouting, glancing round |
| `CHEER_STAND` | 1 | from a bench, 2.7-3.3 s: weight forward and hands pushing off, the hips forward past the seat edge with the thighs still level, then the legs down to stand (by 0.8 of 3 s), arms thrown up and pumping while bouncing; from about 2 s the legs come up level, then the hips go back onto the seat with a settle. The path stays at the seated root throughout (see Seating). Ends seated: the legs stay seated while the cue is in force, the arms go back to the pose |
| `TALK` | L | the leading hand (70% right) gestures in phrases with beats on the stressed syllables, the other joins now and then; head nods on the beats, turns and tilts; a slight lean in |
| `WHISPER` | L | leans in toward where the body faces (turn the actor to the listener with `look`), a hand cupped by the mouth (70% the right), head bowed and tilted in, shoulders up |
| `NERVOUS` | L | wringing hands in front, then dropping them and fiddling; darting glances (quick turns, then a hold), frequent weight shifts, a slight rock; for waiting first-years |
| `WAVE` | L | a big wave (Hagrid): the right arm winds up and rises, then swings side to side like a pendulum (1.2-1.6 a second), the body rocking against it |
| `HANDS_CLASPED` | L | the formal stance (McGonagall): hands together at the waist, chest and chin up, a slow nod, a thumb fidget now and then |
| `READ_SCROLL` | L | a scroll held open in both hands at reading height, head bowed 24 degrees; the head runs slowly along each line and flicks back (1.4-1.9 s a line) and drifts down the page |
| `REACH_PLACE` | 1 | 1.7 s: lowering something onto a seated head in front, both hands (the left trails): a wind-up, up and over in an arc (highest at tick 11), down to shoulder height about 0.75 block in front at tick 19 (`HumanMotion.REACH_PLACE_TICKS`: put the `equip` there) as the body leans in and the head looks down, a lift as the hands let go, the arms home by 1.7 s |
| `SIT_DOWN` | 1 | 1 s: a glance down at the seat, arms out for balance, weight forward, the legs rising level in front first (by 0.45 s), then the hips back and down onto the seat (steering the root itself, see Seating), hands bracing, a settle of the torso. Ends seated: the legs stay seated (and life seated) while the cue is in force |
| `STAND_UP` | 1 | 1 s: weight well forward (30 degrees) with hands pushing on the knees, the hips forward off the seat with the legs still level, then the legs swinging down (vertical by 0.9 s), arms swinging back with the rise. Ends standing: the legs go back to life (and walk) while the cue is in force, even if a seated pose is still in force |

**Layering**, bottom to top: the model's own animation (the head follows `look`), life, then the pose cue and the clip cue in the order they were cued (the later one wins on the parts both drive: a `CLAP` cued after a seated pose claps with the arms and keeps the pose's legs; a pose cued after a clip overrides the clip on the parts the pose names), then `limbs` (always last). A pose that names no part (`"standing": {}`) just hands everything back.

**Seating** (geometry: `HumanMotion` seat geometry, mirrored for generators in `build_scripts/pensieve_scenes/human_motion.py`, kept in step by `human_motion_cases.json` and `HumanMotionTest.pythonMirrorAgrees`; `python human_motion.py` checks the mirror, `--write` rewrites the cases after a deliberate change to both sides). The player model is drawn at 15/16 size from a 1.501 origin, so the hip pivot is `0.7041 * scale` above the feet root (not 0.75), and a leg box (4 px wide, 12 long, plus the 0.25 px pants layer all round) hangs 2.25 px (`0.1318 * scale` blocks) below the hip when level. Rules:
- Seated root: `y = seat_top - 0.5722 * scale` (`seated_root_y(seat_top, scale)` = seat top + leg half width - hip height), x/z at the hip's spot on the seat. That puts the bottom of level thighs exactly on the seat top. Bench (top 0.5): 0.0708 at 0.75, -0.0150 at 0.9, -0.0722 at 1.0, -0.3583 at 1.5. The old `seat_top - 0.75 * scale` sank the legs into the seat.
- Seated pose: legs `[-90, 8, 0]` right and `[-90, -8, 0]` left (the y splay does not change the height). Name only the legs, so life and the clips own the arms. Any pitch other than -90 hangs lower (`leg_lowest_below_hip(pitch, scale)`: 2.25 px at -90, about 7.2 px at -65): a leg angled down (-60 to -75, under a table) clears only if the hip sits near the seat's front edge, so check it with `leg_box` against the set.
- Seat geometry the clips assume: the seat front edge 0.5 ahead of the seated hip (`SEAT_EDGE_AHEAD`); standing up, the hip stands `stand_ahead(scale)` = 0.5 + leg half width + 0.05 ahead of the seated hip (0.649 at 0.75, 0.669 at 0.9, 0.682 at 1.0), on the floor.
- Sitting down (`SIT_DOWN`, 1 s): have the path at the standing spot (`stand_ahead` in front of the seated hip, feet on the floor) at the cue `t`, and at the seated root by `t+1s`; how it gets there in between does not matter (a jump, a line, an ease), because the clip steers the root itself from the path's position at `t` to its position at `t+1s`. Its order: the legs rise level in front (`-90 * smooth((s-0.05)/0.40)`, level by 0.45 s) while the hips stay put, then the hips go back over the seat (`smooth((s-0.30)/0.45)`) and down onto it (`smooth((s-0.50)/0.35)`; when the seated root is higher than the standing one, as for 0.75 on a bench, up first instead: `smooth((s-0.05)/0.35)`). Cue the seated pose (blend 1) at `t+1s`. The gait is held off while it runs.
- Standing up (`STAND_UP`, 1 s): the reverse; path at the seated root at `t`, at the standing spot by `t+1s`. The hips come forward off the seat (`smooth((s-0.15)/0.40)`, vertical `smooth((s-0.10)/0.40)` when rising, `smooth((s-0.55)/0.30)` when dropping) with the legs still level, and only then the legs swing down (`-90 * (1 - smooth((s-0.55)/0.35))`, vertical by 0.9 s). Cue a pose without legs (or none) by `t+1.1s`, before the next anim cue.
- Cheering up off the bench and back (`CHEER_STAND`): the path stays at the seated root; the clip moves the hips forward by `stand_ahead` and up by `stand_rise` (seat assumed 0.5 above the floor) before the legs drop, and back the same way (`cheer_stand_curve`).
- In a generator, sample `sit_down_root` / `stand_up_root` / `cheer_stand_root` and `leg_box` through each clip and assert the corners stay out of solid cells (the hall bench, table and stool).

Dev scene: `run/pensieve_dev/dev_motion.json` (every clip side by side, a bench row with CLAP over an old arms-down pose, CHEER, CHEER_STAND at 0.75 and 0.9, a SIT_DOWN / CLAP / STAND_UP cycle, REACH_PLACE with the hat equipped at the touch-down, walkers at 0.6, 1.4, 2.5 and 4.5 blocks/s plus a first-year and Hagrid, a head-lead turner and a `life: false` statue).

### Custom poses (top-level `poses`)
`"poses": { "slump": { "head": [40,0,0], "right_arm": [-20,0,5] } }` - part to absolute `[x,y,z]` degrees (no offsets). Use a name in an actor's `poses` cue. ### `events[]`
Common keys: `t`, `kind`, `id`, `at`, `volume`, `pitch`, `count`, `spread`, `duration`, `yaw` (effects only), `style` (`enchanted_ceiling`, `sky`, `crowd` and `crowd_react` only), `box` (`letter_flood` only), `rows` (`crowd` only), `intensity` (`light_rays`, `eyes_peek`, `wand_choice`, `rough_sea`, `rain` and `crowd` only). An event's `at` may be fractional (`[46.5, 21, 22.5]`) except a `block` event's, which must be whole blocks. `kind` is required, `id` is required for all kinds. `music` and `voice` take only `t`, `kind`, `id`, `volume`; `sfx` also takes `loop` and `duration` (see the `sfx` row).
| kind | id | uses | effect |
|---|---|---|---|
| `block` | block id | `at:[x,y,z]` | the server places that block at `t` (a door slams, a torch lights). Removed with the set |
| `sound` | sound id (`minecraft:entity.lightning_bolt.thunder`, `hogwartsmagic:...`) | `volume` 1, `pitch` 1, optional `at` (none = heard in your own ears) | plays once at `t` |
| `particles` | plain particle id (`minecraft:poof`, `minecraft:end_rod`) | `at`, `count` 1 (max 500), `spread:[x,y,z]` box half-size | a burst; parameterised particles (dust, block) cannot be used |
| `effect` | `summoning_ritual`, `lightning`, `dark_mark`, `grey_edges`, `patronus_light`, `fiendfyre_rings`, `eyes_open`, `eyes_close`, `eyes_peek`, `letter_flood`, `enchanted_ceiling`, `light_rays`, `floating_candles`, `wand_choice`, `rough_sea`, `rain`, `sky`, `crowd`, `crowd_react` | `at`, `duration` (`crowd` also `rows`, `style`, `intensity`, `count`; `crowd_react` also `spread`, `style`; `rough_sea` also `spread`, `intensity`; `rain` also `spread`, `intensity`; `letter_flood` also `yaw`, `count`, `box`, `spread`; `enchanted_ceiling` also `spread`, `style`; `sky` also `style`; `light_rays` also `yaw`, `spread`, `intensity`; `eyes_peek` also `intensity`; `wand_choice` also `intensity`; `floating_candles` `spread`, `count`, no `duration`) | scripted set-pieces below |
| `music` | sound id (`hogwartsmagic:pensieve.music.<file>`) | `volume` 1 (0 to 4) | a soundtrack cue, played whole from `t` |
| `voice` | sound id (`hogwartsmagic:pensieve.voice.<file>`) | `volume` 1 (0 to 4) | a spoken line, played whole from `t` |
| `sfx` | sound id (`hogwartsmagic:pensieve.sfx.<file>`) | `volume` 1 (0 to 4) | a non-positional sound effect on `SoundSource.AMBIENT`, full pitch, no echo, no ducking; played whole from `t`, stops at once when the memory ends. `"loop": true` repeats the file seamlessly (the client engine loops it, so cue loop files such as the Flying `crowd_bed`, `rain`, `lawn_air` and `snitch_flutter` once, never re-cue them) until `duration` ticks have passed, or until the scene ends when `duration` is absent, then fades out over 20 ticks; `duration` is only valid with `loop` and must end inside the scene. A scene's end fades a loop instead of cutting it |

Effects: `lightning` - one visual-only bolt with thunder; `eyes_open` / `eyes_close` - the viewer's eyelids, screen-only (`at` ignored), default 2 s (40 ticks): two black lids each covering up to half the screen with a soft 24 px edge; `eyes_open` starts fully shut, stays shut for 30% of `duration`, half-opens for a blink (peak at 45%), shuts again by 55%, then opens fully by the end (ease-out) and is gone after `duration`; `eyes_close` starts open and shuts by the end of `duration` (ease-in) and then stays shut until the scene ends (it never expires); the most-closed running lid wins (`pensieve/scene/Eyelids`). `eyes_peek` - the eyes open just a little and close again, screen-only, default 3 s (60 ticks): it starts fully shut, the lids part to a slit over the first 30% of `duration` (ease), hold it until 70%, then shut by the end and stay shut until the scene ends (like `eyes_close`). How far they open is `intensity`, 0.05 to 1 (default 0.35, a third: `Eyelids.peekOpen`; `intensity` means this only on `eyes_peek`). Dev scene: `run/pensieve_dev/dev_crowd.json` from `dev_crowd.py` (a 3,000-seat bowl in four house stands under a storm sky: a goal, a gasp, an erupt, a sit and a chant); in a `dev_` scene the client log gets a `Pensieve crowd:` line every 5 s with the crowd's CPU time and upload (vertices and KB) per frame. Keep each row's head block (seat top + 1.2) in air: a head inside an opaque block reads light 0 and draws black.

**Music and voice cues** (`client/pensieve/MemoryAudio`). `sound` events go through `MemorySounds`: volume x0.75, pitch x0.92, an echo 6 ticks later, positioned in the world, never stopped. That is wrong for a soundtrack or a spoken line, so use `music`/`voice` (or `sfx` for effects) for those:
- Both are non-positional (`Attenuation.NONE`, no `at`), at full pitch and volume, with no echo. `music` plays on `SoundSource.MUSIC`, `voice` on `SoundSource.VOICE`. Register the OGG as `pensieve.music.<file>` / `pensieve.voice.<file>` in `ModSounds` and `sounds.json` (`"stream": true` for music, no subtitle); `id` is checked like a `sound` id.
- `sfx` is the same but on `SoundSource.AMBIENT` (register as `pensieve.sfx.<file>`). Like `voice` it is skipped when `t` is more than 5 ticks past for a late joiner, and it stops at once when the memory ends (`pensieve/scene/CueKinds.stopsAtEnd`: true for `voice` and `sfx`, music fades). It neither ducks music nor is ducked.
- Ducking: while any voice plays, every music instance eases to 45% volume (0.08 per tick) and back after it ends.
- Ending: when the memory ends for any reason (end, leave, yank, basin broken, death, disconnect, a new memory starting) voices and sfx stop at once and music fades out over 20 ticks. While memory music plays, vanilla background music is held off.
- Cues play the whole file from `t`: bake fades into the file, and overlap consecutive tracks by about 2 s to crossfade.
- Late joiners: Minecraft cannot seek into an OGG, so a cue whose `t` is already past (more than 5 ticks) when the viewer joins is skipped, like any one-shot event. A viewer who joins mid-track hears silence until the next cue.


### `words[]`
`{ t, by?, text, narration?, duration?, size? }`. With `by` (an actor id) the line shows as `<name> text` at the bottom left for 8 s; without `by`, plain text. `"narration": true` shows centred silver italic text that fades in and out over `duration` (default 80 ticks). `size` (1 to 4, default 1; narration only) scales the narration text about its centre, e.g. 3 for a large title; the wrap width shrinks to match. Never written to real chat.

`{ t, text, subtitle: true, speaker?, duration? }` is a film-style subtitle: centred near the bottom in white on a soft dark box, an optional small muted-gold `speaker` name before the text, fading in and out over `duration` (default 80 ticks; pass the voice clip length), wrapped at 70% of the screen width, overlapping subtitles stack upward. It needs no actor or name tag, takes `{viewer}`, and is hidden under shut lids and chain black like spoken lines. The validator rejects `subtitle` with `by` or `narration`, and `speaker` without `subtitle`.

### `camera[]`
`{ t, pos:[x,y,z], look_at?, fov?, roll?, ease?, cut? }`, sorted by time. Defaults: `fov` 70, `roll` 0, ease `in_out`.
- `pos` is the camera (eye) position. `look_at` is `"actor:<id>"` (that actor's eye) or `[x,y,z]`; without it the camera looks straight along +Z.
- A broom rider's eye is tilted with its broom about the rider's root (`scene_engine.rider_eye`); a broom's eye is its seat point.
- A player actor's eye (`look_at: "actor:<id>"`) eases between 1.62 and 1.27 (times scale) over 4 ticks (smoothstep) from each `sneak`/`stand`, so a crouch does not jolt the camera (`EyeEase`); a generator mirrors it as `actor_eye_height`.
- Between keys position, look target, fov and roll are interpolated (so `look_at` can slide from one actor to another).
- `"cut": true`: the camera holds the previous key until this key's `t`, then jumps to it with no blend. Use for hard cuts. Put the cut key slightly before the action it should catch. A cut is a hard cut anywhere in the set: the client meshes the sections round each shot a cut lands in (camera and `look_at` point, within 40 blocks) up to 3 s ahead (`client/pensieve/SetWarmup`), and on the frame the camera jumps it rebuilds the visible-section list at once (`PensieveOcclusionGraphMixin`), so the new shot never streams in. A shot whose interest is farther than 40 blocks from both its camera and its `look_at` point can still show far sections arriving: aim `look_at` at what matters.
- Before the first key it holds the first; after the last it holds the last.
- `"ease": "spline"` (camera keys only): the segment ending at that key is a cubic through the neighbouring keys, so position, look target, fov and roll keep a continuous velocity through every key of a run of spline keys (C1 in time, even for uneven spacing; Catmull-Rom when keys are evenly spaced). Use it for any moving shot keyed densely (a tracking shot sampled from an actor's path every few ticks, an orbit, a crane): with `linear` keys the speed and the pan rate step at every key, a visible hitch each key, and with `in_out` the camera stops at each one. Where a run meets an eased segment it takes that segment's speed (rest next to `in_out`, so end a run with an `in_out` key to settle; the straight-line speed next to `linear`). Next to a cut, the first key or the last key the end is natural: it keeps its speed into the key. A two-key run is a straight line. Evenly spaced keys overshoot by at most about 7% of a step (a sudden step between flat runs, the worst case); keep spacing roughly even and let the keys follow a smooth path, not a jagged one. A Python check that mirrors the camera (`engine_cam`) must mirror this too: a Hermite per segment, velocity `m_i = (h1*d0 + h0*d1)/(h0+h1)` at an inner key (`d0`, `d1` the secants either side, `h0`, `h1` their lengths in ticks), the eased neighbour's end/start slope times its secant at a run end (`linear` 1, `in` 0 then 3, `out` 3 then 0, `in_out` 0), else `(3*secant - m_other)/2`.
- The scene clock the camera, actors and effects read is eased on the client: it follows the server's game time but never jumps with vanilla's 1 Hz time sync. Every sync is a sample; the server's time and speed are a least-squares line through the recent samples that fit one line, kept under the real-time schedule (a server racing back after a hitch stops where it meets it). The playback speed follows that line through a critically damped loop and changes by at most 0.05 a tick, so it never lurches or overshoots. On a full-speed server it runs at exactly 1. On a slow server the whole memory plays at the server's real speed, within about a tick of it. When the server changes speed the clock is up to about 10 ticks off while it catches up; during a stall it runs on by the stall, then slows or holds, never backward. Syncs held up in transit and released together are not taken for a race. It snaps only past 45 ticks behind or 100 ahead. Within 0.02 of a tick it lands exactly on the server's time, so tick-time actions fall on whole ticks. Worn items are switched on the frame the clock reaches their cue, the same frame a limb step keyed on that moment lands.

### Scene hooks and hand-overs (server code, not scene keys)
A scene can be driven by mod code as well as by its own clock (`pensieve/PensieveSessions`):
- `addSceneEnterListener(sceneId, (player, session) -> ...)`: told on the server each time a viewer starts watching that scene with its clock running: its PLAY begins with them inside, they cross into it already playing, or a hand-over (`next` or `handOver`) moves them in. Once per viewer per session; a scene handed over to itself counts again. Previews and dives call it too, so a listener checks for its own players. Example: the Sorting opens its quiz when its player enters `sorting_choice`.
- `addSceneTimeoutListener(sceneId, listener)`: told for each viewer inside when the scene's clock runs out with no `next` standing by. If it calls `handOver` the viewers go there (to the same id to loop a hold scene) instead of going home.
- `handOver(player, sceneId)`: cut now to another scene, whatever the clock says. The scene is built ahead as a standby (replacing a `next` one), the scene on screen fades to black over 20 ticks (`HANDOVER_FADE_TICKS`, the chain fade), and once the fade is over and the set is built every viewer moves over exactly as at a chain's end (same return point, body, chain root and home callback; the new scene fades in from black). It may name the scene playing now (a loop) or one the chain already played. Safe while the current scene is still building and while a hand-over is under way (the same id again changes nothing, another id replaces it). False when the player is not inside, is already leaving, or the scene does not load. On the client the new session is told apart by its origin, so a scene handed to itself restarts its actors, events and camera.
- `startSolo(player, sceneId, context)`: a solo start with a start context that fills the scene's placeholders for the whole chain (`ItemText.CONTEXT_WAND`: the item id `{viewer_wand}` becomes). The 2-argument `startSolo` is the same with an empty context (the held wand, then Harry's).
- So a scene meant to be reached by `handOver` or to loop needs nothing special in its JSON; a hold scene simply gets a long `length` as a backstop, and its own content should still read well if it loops.

## Coordinates
- Origin = the block where the set is anchored; viewers float one block above it before the camera takes over. Actors with `pos:[0,0,0]` stand on top of the block layer at y = -1, so lay floors at `y: -1`.
- Y is up. X east, Z south. Yaw follows Minecraft: 0 = facing +Z (south), 90 = facing -X (west), 180 = -Z (north), -90 = +X (east). Pitch: positive = looking down, negative = up, +-90 max. `look_at` and the camera derive yaw/pitch from positions for you; you only write yaw/pitch for actors' `look`.
- Event `at` and `set` coordinates are integer block corners (decimals are rounded). Actor `path` and camera `pos` are relative to the origin block's corner and take decimals, so use `.5` to centre on a block (`[0.5, 0, 0.5]`).
- Everything must stay within `radius` (default 40, max 200) of the origin in X and Z, or validation fails for fills/disks/templates/features.

## The loop
1. Client closed? Edit nothing in `build/` and **never run gradle while the dev client is running**: gradle rewrites `build/sourcesSets/main` and the live client throws `ClassNotFoundException`. Check with `tasklist | findstr java` (the GradleDaemon is fine; a Minecraft java process is not).
2. Set the config `pensieveDevSceneDir` (`run/config/hogwartsmagic-common.toml`) to a folder; relative paths are against the game run dir `run/` (so `../src/main/resources/data/hogwartsmagic/memories`). `/pensieve preview` then reads `<dir>/<id>.json` fresh from disk each time, so no rebuild between edits.
3. Write the scene to `src/main/resources/data/hogwartsmagic/memories/<id>.json`. For anything bigger than a few events, write a Python generator in `build_scripts/pensieve_scenes/<id>.py` (the shipped ones are there, with `scene_common.py` for template reading and the JSON layout; run them from the repo root) and commit it with the scene. Files starting with `_` are not scenes. `<id>` is lowercase with underscores.
4. In the dev client (op): `/pensieve preview <id>` plays it from the start with no basin. `/pensieve validate [id]` only checks scenes loaded from the registry (built into the game), NOT dev-dir files: during the edit loop, `preview` is the validator (it validates the fresh file and reports problems), and validate is for shipped scenes after a build. `/pensieve list` shows loaded ids. `/pensieve leave` or the **X** key leaves a memory.
5. Screenshot, read the chat for part/animation errors, edit the JSON, then leave (press **X**) and run `/pensieve preview <id>` again; a preview cannot be restarted while you are inside the memory.
6. With the client closed: `./gradlew test --tests "*SceneDataTest*"` parses and validates every shipped scene (`./gradlew test` runs the lot). It must pass before committing.
7. Commit the scene (and any new skin) - and ask the user to push.

Size caps: scene JSON max 900,000 characters and 1,000,000 UTF-8 bytes (the clientbound custom payload limit is 1 MiB = 1,048,576 bytes, so a scene of mostly non-ASCII text hits the byte cap first), scene id max 256 (a bigger scene is refused when sent to the client, with a log line naming both sizes).

`SceneDataTest` is narrower than the game: its entity types are only the mod's own entities, `player`, and a fixed `VANILLA_MOBS` list in `SceneDataTest.java` (zombie, skeleton, villager, armor_stand, bat, spider, cave_spider, wither_skeleton, evoker, vindicator, witch, horse, wolf, cat, fox, sheep, cow, pig, chicken, squid, glow_squid, salmon, cod, lightning_bolt). Any other vanilla mob (even a valid one in game) fails the test until you add it to that list. Its `features` accept only `minecraft:` ids, and its `sounds`/`particles`/`blocks`/`items` accept any `minecraft:` id but only mod ids that are registered in source.

Validation rules to remember: player `anims` names must be player clips, `life` is only for players; ids are namespaced (`minecraft:`, `hogwartsmagic:`), `player` is the only bare entity id, spells are bare, skins are bare names from `_skins.json`; pose cue names must be a preset or a custom pose; a `cast` needs `spell`; actor ids must be unique; `words[].by`, `look_at` and `target` must name an existing actor.

## Giving a scene an item (so players can pour it)
Players get a scene through an item that implements `PensieveMemory`. Existing: `chamber_memory` -> scene `chamber`, `summoning_memory` -> scene `summoning` (both `StoryMemoryItem`, in `ExampleMod`), `patronus_memory` -> `lake_patronus` (`StoryMemoryItem`; given once, with a silver chat line, the first time a player learns Expecto Patronum: `MagicBookItem.grantPatronusMemory`), `cave_memory` -> `locket_cave` (`CaveMemoryItem`). For a new scene, only if the user wants an item:
- Register in `ExampleMod`: `ITEMS.register("<id>_memory", () -> new com.hogwartsmagic.pensieve.StoryMemoryItem(new Item.Properties(), "<scene id>"))`.
- Add it to the creative tab list next to `output.accept(SUMMONING_MEMORY.get())`.
- Add `item.hogwartsmagic.<id>_memory` to `lang/en_us.json`, and `models/item/<id>_memory.json` (copy `chamber_memory.json`) plus a 16x16 texture `textures/item/<id>_memory.png`.
- Scene ids must match exactly; a missing scene just logs and plays nothing.
Op preview needs no item.
Story triggers (a scene started by an event, not an item): `PensieveSessions.startSolo(player, sceneId, context)` plays it for one player; a home listener (`addHomeListener`, `chainRoot` = the scene that began the chain) follows up when they are back. The Sorting Hat starts `sorting` this way, and the first wand bought from a wandmaker starts `wand_wall` (`pensieve/WandMemory`: the trade hook, a tick later (it runs inside the trade click), closes the trade screen, then `tryStart(player, boughtWand)` with the context `{"viewer_wand": <item id>}`; if it refuses, the old `OllivandersCeremony` plays; the once-only flag is the ceremony's, set when the memory ends or is left after it started (leaving during the build or fade does not count), not on a yank or disconnect; `/ollivanders` replays it with the held wand). The first time a new player opens their Hogwarts letter, `letter` plays (`pensieve/LetterMemory`: `ModEvents.spawnFirstYearInvite` sets the `LetterMemoryPending` flag in `PlayerPersisted`, so old saves never have it; `HogwartsInviteItem.use` calls `tryStart` first and sends the letter screen packet only if it returns false; if `letter` is missing it returns false and logs once; a second use while the memory runs or the wake is playing is swallowed). When the player is home (any exit of a chain begun by `tryStart`) the letter screen opens, after `WAKE_DONE_TICKS` when the chain ended in a wake; the flag is cleared only when the chain ended with `END` in `letter_hut` (a chain that ended early, a leave or a yank opens the letter but plays the memory again next time); a death drops the memory and opens the letter after the respawn, a disconnect opens nothing at the next login (the flag replays the memory on the next use). A trigger must start the memory only after the action it follows has completed, so the player's items are never at risk. The first time a sorted player mounts a broom, `flying_<house>` plays (`pensieve/FlyingMemory`: `BroomEntity.interact` schedules `tryStart` for the next server tick, for a real player only; the chain is `flying_<h>` -> `_chase` -> `_match` -> `_snitch`, and a mob mounting with `startRiding(broom, true)` never triggers it). `tryStart` refuses (the player just flies) when they are unsorted, have `FlyingMemorySeen` set in `PlayerPersisted` (every player gets it once, old saves included), are inside a memory, or the scene is missing (logged once). While they are away the broom is parked (`BroomEntity.holdFor`: no gravity, no motion, nobody can mount it, not saved) and its chunk is kept loaded by a region ticket. At home, any exit puts them back on it if it is within 64 blocks (after `WAKE_DONE_TICKS` when the chain ended in a wake), else they stand where they mounted; the flag is set only when the chain ended with `END` in `flying_<h>_snitch`; a death or logout releases the broom with no remount. The first time a player helps bring down a Hungarian Horntail, `first_task` plays (`pensieve/FirstTaskMemory`: a `LivingDamageEvent` hook records each player `DamageSource.getEntity()` resolves to, so an arrow or spell counts for its shooter or caster and a pet's bite does not count for its owner; `LivingDeathEvent` sets `FirstTaskMemoryPending` in `PlayerPersisted` for every recorded player within 60 s and 64 blocks, whoever or whatever got the kill, and the memory starts 21 ticks later, after the death animation; a busy, dead, waking or logged-out player stays pending and is retried every 20 ticks, or 100 ticks after a login; the chain is `first_task` -> `first_task_arena` -> `first_task_chase` -> `first_task_egg`, which wakes, and `FirstTaskMemorySeen` is set only when it ended with `END` in `first_task_egg`, so a leave or a yank plays it again at the next kill; there is no reward and no house gate; the memory puppet `MemoryHorntailEntity` is never recorded).
